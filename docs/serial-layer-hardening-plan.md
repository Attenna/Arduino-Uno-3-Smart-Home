# 串口层加固方案（P0）

> 状态：**阶段一已实施并部署验证**（P0-1 读取线程 + P0-2 空闲心跳 + `get_serial_health` 健康度）；P0-3（协议 id / 固件 V2.6）按计划押后。
> 范围：`voice` 容器内的串口层（`PC_Test/mcp_home_server.py`）+ Module B 固件（如采纳 P0-3）。
> 触发背景：A 板读异常刷屏、MCP 调用洪泛、风扇"自己转 / 关不掉"——四个现象指向同一类根因。
>
> **实施记录**：健康度通过 MCP 工具 `get_serial_health` 暴露，可 `POST http://<派>:8101/tool -d '{"name":"get_serial_health","arguments":{}}'` 读取（web 是 `--no-serial`，暂不经 `/api/status` 透传，属 P1）。

---

## 0. 问题定性

四次事故的**共同根因类别**不是某个具体 bug，而是三个结构性缺陷：

| 缺陷 | 表现过的故障 |
|------|-------------|
| **状态真值不可观测**（读不到硬件就退回"上次命令值"） | 风扇"关不掉"（DB 被当硬件真值） |
| **静默失效**（ACK 成功但硬件没动 / 上报被丢） | 风扇"自己转"；B 板复位与引脚自愈告警全部不可见 |
| **生命周期零散**（谁在什么时候重连、由谁触发，散落各处） | A 板读异常刷屏 12h 不重连；B 板只在"命令超时"才重连 |

**核心结论**：Module A 有常驻读取线程（[_read_a_loop](../PC_Test/mcp_home_server.py)），Module B **没有**。B 板的"读响应"内联在 [_send_b_once](../PC_Test/mcp_home_server.py) 里"发一条等一条"；**没有命令发送时，B 板主动上报的帧无人消费**，会被下一次清缓冲丢掉。

---

## 1. 现状（代码事实）

| 能力 | Module A | Module B |
|------|----------|----------|
| 常驻读取线程 | 有（`module-a-reader` 守护线程，独占消费） | **无** |
| 异步帧分类 | 有（`ready` / `data` / `event`） | **无**（`ready` / `alert` / `state` 被丢） |
| 断线自愈 | 设备级异常 → 退避重开 by-id | 仅"命令响应超时"→ 重开 |
| 日志限频 / 恢复事件 | 首条即时 + 30s 摘要 + 恢复一行 | 无 |
| 健康度计数 | 无（只有日志） | 无 |

当前 V2.5 固件已能让风扇引脚自愈并上报 `fan_pin_reclaim`，但**服务端只在"恰好有命令要发"的那一刻顺手捞一次**（`_log_b_async()`）——这是权宜，不是机制。

**协议现状**：B 板下行 `{cmd, action, ...}`；上行 `response` **不回显任何请求标识**。多命令只能靠客户端串行（`_b_lock`）+ 清缓冲兜底。

---

## 2. 目标 / 非目标

**目标**
1. B 板与 A 板同等对待：常驻读者、异步帧分类、断线自愈、限频日志。
2. 任何"主动上报"（复位横幅、引脚自愈告警、状态帧）**不再丢失**。
3. 串口健康度**可观测**（重连次数、B 板复位次数、最后自愈时间），出问题一眼可见。

**非目标（明确不做）**
- 不改 A/B 板之间的语义，B 板仍"只执行不决策"。
- 不做 web 侧硬件真值回读（属 P1，另案）。
- 不复活 HA/MQTT 通道。
- 本次不动 `DeviceGate` / 自动化引擎逻辑。

---

## 3. 改造项

### P0-1　B 板常驻读取线程 + 异步帧分类

**做法**：新增 `_read_b_loop`（守护线程），成为 B 板串口的**唯一读者**。

```
                 ┌─ response ─→ 按 id 唤醒等待者（P0-3 前：唤醒"当前唯一在飞"的等待者）
B 串口 ─ 读者 ──┼─ ready ────→ 记 B 板复位（计数 + 时间 + 版本）
                 ├─ alert ────→ 记告警（引脚自愈等），进健康度
                 ├─ state ────→ 更新"硬件回读值"缓存
                 └─ 噪声 ─────→ 限频日志，不阻塞
```

**发送路径改造**：`_send_b` 从"写 + 内联读"改为"登记等待者 → 写 → 等事件（带超时）"。等待者由读取线程唤醒；超时仍走现有 `_reopen_b()`。

**收益**：空闲期上报不再丢；`_log_b_async()` 从权宜变成机制的一环（可保留为兜底）。

**风险**：读取线程与发送路径竞争 → 用"单一读者 + 等待者表"消除，写仍走 `_b_lock`。

### P0-2　空闲心跳 + 自愈（补齐"空闲期坏掉不自愈"）

**做法**：低频只读心跳 `{"cmd":"system","action":"status"}`（建议 10s）：

- 有响应 → 刷新"B 板在线 + 硬件回读值"；
- 连续无响应 → 按与 A 板**同一套**退避策略重开 by-id（1→2→4→8→10s 封顶），并打**首条 + 摘要 + 恢复**三段日志。

**收益**：B 板空闲期损坏能被发现并自愈，而不是等用户下一次操作才暴露成"点了没反应"。

**注意**：`system/status` 是纯只读命令，不会改变任何执行器状态。

### P0-3　协议加请求 id（需固件 V2.6）

**做法**：下行允许携带 `"id": <整数>`；上行 `response` 原样回显 `id`。无 `id` 的命令保持现行为（兼容旧客户端/curl）。

- 固件：`Command` 结构加一个 `id` 字段（[CommandParser.h](../module-b-output/src/core/CommandParser.h)），`respondOk/respondError` 回显（[Protocol.cpp](../module-b-output/src/Protocol.cpp)）。
- 服务端：等待者表按 `id` 索引，可安全**丢弃迟到响应**，并可并发下发（读命令不再互相串行）。

**收益**：消除"迟到响应被当成本次结果"这一整类隐患（现在靠清缓冲兜底）。

**可选**：也可以不做 P0-3，继续用"单飞 + 清缓冲"。做了 P0-1/P0-2 之后 P0-3 是**锦上添花**，不是必需。

## 4. 分阶段与迁移（关键：先做不烧录的部分）

| 阶段 | 内容 | 是否需烧录 | 可回滚性 |
|------|------|-----------|---------|
| **阶段一** | P0-1 + P0-2（纯 Python） | 否 | 高（回退镜像即可） |
| **阶段二** | P0-3 + 固件 V2.6（仅当评审认为必要） | 是 | 中（需回烧） |

**推荐**：先只做阶段一。它能覆盖"上报丢失 / 空闲期不自愈"这两个已发生过的故障类型；阶段二等真正出现"迟到响应导致错判"的证据再做。

**兼容性**：阶段一对固件无要求，V2.5 及更早固件均可；读取线程对未知 `type` 一律走"噪声"分支。

## 6. 验收标准

1. **上报不丢**：拔插 / 复位 B 板，日志能看到 `ready` 帧 + 复位计数递增；`fan_pin_reclaim` 一条不漏。
2. **空闲自愈**：空闲期拔掉 B 板 USB → 心跳失败 → 退避重连 → 插回后自动恢复，全程有"首条/摘要/恢复"三段日志。
3. **不劣化**：控制命令延迟不增加（对照 `[HTTP] /tool` 耗时）；超时率不升高；`/api/status` 仍正常。
4. **健康度可见**：`/api/status`（或新只读接口）能读到 A/B 重连次数、B 板复位次数、最后自愈时间。
5. **单测**：帧分类、迟到响应丢弃、心跳退避节拍、等待者超时唤醒——抽纯逻辑函数后写成回归用例。

## 10. 实测发现：物理拔插恢复不了（Docker 设备映射限制）

阶段一部署后做了一次**物理拔插验证**，结果分两半：

**代码侧完全按设计工作**（这是阶段一的价值所在）：

```
[B] 读线程异常: device reports readiness to read but returned no data ...   ← 限频，只 1 行
[B] 心跳失败 1/3 次: error: 串口写入失败 write failed: [Errno 5] Input/output error
[B] 心跳失败 2/3 次: ...
[B] 心跳失败 3/3 次: ...
[B] 串口重开失败: [Errno 6] No such device or address: '/dev/serial/by-id/...0250-if00'
（之后每 30s 一个周期持续重试）
```
以前这种情况是**完全静默**的（要等用户下次操作超时才暴露），现在有清晰、限频、持续重试的日志。

**卡住的是容器设备节点**（与本次改动无关，属既有缺口）：

| | 拔插前 | 拔插后（宿主机） | 拔插后（容器内） |
|---|---|---|---|
| 路径 | ttyACM3 | ttyACM0 | 仍是旧节点 |
| 主/次设备号 | `166,3` | `166,0` | **`166,3`（死节点）** |

Docker 的 `devices:` 在**容器创建时**解析一次并固化设备号；物理拔插导致重新枚举后主/次设备号变化（3→0），容器里的旧节点永久失效 → `Errno 6`，**任何用户态代码都救不回来**。A 板同理。

**可行的修法**（需评估，都属配置层）：

| 方案 | 做法 | 代价 |
|------|------|------|
| ① 整目录透视 | `volumes: - /dev:/dev` + `device_cgroup_rules: ['c 166:* rmw']` | 容器可见宿主全部设备，隔离性下降 |
| ② 特权容器 | `privileged: true` | 最省事，权限最大 |
| ③ 接受 | 物理拔插后 `docker compose up -d --force-recreate voice` | 不改配置；靠维护动作恢复（本次就是这样恢复的） |

> 结论：**阶段一解决的是"串口级故障"（USB CDC 抖动、句柄损坏、固件挂死——节点仍有效）**；
> **物理拔插**是容器设备映射问题，需要单独决议是否加固。
